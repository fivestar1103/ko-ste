# git rebase vs git merge: 신입 개발자를 위한 한눈에 보는 정리

브랜치에서 작업하다 보면 `main`에 올라온 최신 변경사항을 내 브랜치에 가져와야 할 때가 있습니다. 이때 쓰는 두 가지 방법이 `merge`와 `rebase`입니다. 결과물(코드)은 같아도 **히스토리가 남는 모양**이 다릅니다.

## git merge: 두 갈래를 합친다

```bash
git switch feature
git merge main
```

두 브랜치의 끝을 합치는 **머지 커밋**을 새로 만듭니다. 기존 커밋은 그대로 남습니다.

```
A---B---C---M   (feature)
     \     /
      D---E     (main)
```

- 장점: 기존 히스토리를 건드리지 않아 안전하고, 언제 합쳤는지 기록이 남습니다.
- 단점: 머지 커밋이 쌓이면 히스토리가 복잡한 그래프가 됩니다.

## git rebase: 내 커밋을 최신 위에 다시 쌓는다

```bash
git switch feature
git rebase main
```

내 브랜치의 커밋들을 `main`의 최신 지점 뒤로 **옮겨 다시 만듭니다.** 그래서 히스토리가 한 줄로 깔끔해집니다.

```
D---E---B'---C'   (feature)
```

- 장점: 일직선 히스토리라 읽기 쉽습니다.
- 단점: 커밋이 새로 만들어지므로(`B` → `B'`) 커밋 해시가 바뀝니다.

## 한 줄 비교

| | merge | rebase |
|---|---|---|
| 히스토리 | 갈래가 그대로 보존됨 | 한 줄로 정리됨 |
| 기존 커밋 | 변경 없음 | 새 커밋으로 다시 생성 |
| 머지 커밋 | 생김 | 안 생김 |
| 안전성 | 높음 | 주의 필요 |

## 꼭 지킬 규칙

> **이미 원격에 push해서 다른 사람이 쓰고 있는 브랜치는 rebase하지 마세요.**

rebase는 커밋 해시를 바꾸기 때문에, 동료의 히스토리와 어긋나 큰 혼란이 생깁니다. 아직 나만 쓰는 로컬 브랜치에서만 사용하세요. rebase 후 push가 필요하면 `--force-with-lease`를 쓰되, 내 개인 브랜치일 때만 사용합니다.

## 실무 가이드

- **내 로컬 작업 브랜치를 최신으로 맞출 때** → `rebase`
- **공유 브랜치(`main` 등)에 작업을 합칠 때** → `merge` (또는 팀 규칙에 따라 PR 머지)
- **잘 모르겠을 때** → `merge`. 덜 깔끔해도 덜 위험합니다.

정답은 없고 **팀의 규칙을 따르는 것**이 가장 중요합니다. 처음 일하는 팀에서는 어떤 방식을 쓰는지 꼭 먼저 물어보세요.
