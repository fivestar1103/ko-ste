# git merge와 git rebase, 무엇이 다를까?

두 명령 모두 **한 브랜치의 변경 사항을 다른 브랜치에 합치는** 데 씁니다. 차이는 **이력(history)을 어떻게 남기느냐**에 있습니다.

## 상황 예시

`main`에서 `feature` 브랜치를 만들어 작업하는 동안, 다른 사람이 `main`에 새 커밋을 올렸다고 해 봅시다.

```
      A---B  feature
     /
C---D---E    main
```

## git merge: 두 갈래를 그대로 묶는다

```bash
git switch feature
git merge main
```

```
      A---B---M  feature
     /       /
C---D---E----
```

- 두 브랜치를 합치는 **머지 커밋(M)**이 새로 생깁니다.
- 기존 커밋(A, B)은 **그대로 유지**됩니다.
- 실제로 무슨 일이 언제 일어났는지가 정확히 남습니다.
- 대신 브랜치가 많아지면 이력 그래프가 복잡해집니다.

## git rebase: 내 커밋을 최신 위치로 옮겨 다시 쌓는다

```bash
git switch feature
git rebase main
```

```
C---D---E---A'---B'  feature
```

- 내 커밋(A, B)을 `main`의 최신 커밋(E) 위에 **새로 다시 만듭니다**(A', B').
- 머지 커밋 없이 **한 줄로 깔끔한 이력**이 됩니다.
- 대신 커밋이 새로 만들어지므로 **커밋 해시가 바뀝니다.**

## 한눈에 비교

| | merge | rebase |
|---|---|---|
| 이력 모양 | 갈래가 그대로 남음 | 한 줄로 정리됨 |
| 기존 커밋 | 유지 | 새 커밋으로 교체 |
| 머지 커밋 | 생김 | 생기지 않음 |
| 충돌 해결 | 한 번에 | 커밋마다 따로 할 수 있음 |
| 안전성 | 높음 | 공유 브랜치에서는 주의 필요 |

## 꼭 기억할 규칙

> **다른 사람과 함께 쓰는 브랜치(이미 push한 브랜치)는 rebase하지 마세요.**

rebase는 커밋을 새로 만들기 때문에, 다른 사람이 이미 받아 간 커밋과 내 커밋이 서로 달라집니다. 이 상태에서 강제 push(`git push --force`)를 하면 동료의 작업이 꼬일 수 있습니다.

## 언제 무엇을 쓸까?

- **아직 push하지 않은 내 로컬 브랜치를 최신 `main`에 맞출 때** → `rebase`
- **작업이 끝난 기능 브랜치를 `main`에 합칠 때, 공유 브랜치를 다룰 때** → `merge`
- 팀마다 규칙이 다르므로, **먼저 팀의 컨벤션을 확인**하는 것이 가장 좋습니다.

한 줄로 정리하면 이렇습니다. **merge는 "있었던 그대로" 기록하고, rebase는 "처음부터 이렇게 작업한 것처럼" 다시 정리합니다.**
