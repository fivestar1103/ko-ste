# git merge와 git rebase, 무엇이 다를까?

브랜치에서 작업을 마치면 그 변경을 다른 브랜치(보통 `main`)에 합쳐야 합니다. 이때 쓰는 대표적인 방법이 **merge**와 **rebase**입니다. 둘 다 "변경을 합친다"는 목적은 같지만, **히스토리를 남기는 방식**이 다릅니다.

## 상황 예시

`main`에서 `feature` 브랜치를 만들어 작업하는 동안, 다른 사람이 `main`에 새 커밋을 올렸다고 해 봅시다.

```
      A---B  (feature)
     /
C---D---E    (main)
```

## git merge: 두 갈래를 "합치는 커밋"을 만든다

```bash
git switch main
git merge feature
```

```
      A---B
     /     \
C---D---E---M  (main)
```

- 두 브랜치를 잇는 **머지 커밋(M)**이 새로 생깁니다.
- 기존 커밋은 **그대로 보존**됩니다. "언제 갈라졌고 언제 합쳐졌는지"가 기록에 남습니다.
- 단점: 브랜치가 많아지면 히스토리 그래프가 복잡해 보일 수 있습니다.

## git rebase: 내 커밋을 "최신 위치로 옮겨 다시 쌓는다"

```bash
git switch feature
git rebase main
```

```
C---D---E---A'---B'  (feature)
```

- `feature`의 커밋 A, B를 `main`의 최신 커밋 E 뒤에 **새로 다시 만듭니다**(A', B').
- 히스토리가 **한 줄로 깔끔**해집니다.
- 주의: A'와 B'는 A, B와 내용은 같아도 **해시가 다른 새 커밋**입니다. 즉, 히스토리를 다시 쓰는 작업입니다.

## 한눈에 비교

| 구분 | merge | rebase |
|---|---|---|
| 히스토리 모양 | 갈래와 합류점이 남음 | 한 줄로 정리됨 |
| 기존 커밋 | 그대로 보존 | 새 커밋으로 다시 작성 |
| 새 커밋 | 머지 커밋 생성 | 생성 안 함 |
| 충돌 해결 | 한 번에 해결 | 커밋마다 해결할 수 있음 |
| 위험도 | 낮음 | 공유 브랜치에서 쓰면 위험 |

## 꼭 기억할 황금률

> **이미 다른 사람과 공유한(push한) 브랜치는 rebase하지 마세요.**

rebase는 커밋을 새로 만들기 때문에, 다른 사람이 기존 커밋을 기반으로 작업하고 있었다면 히스토리가 꼬입니다. 이 경우 `git push --force`가 필요해지고, 동료의 작업을 덮어쓸 위험이 생깁니다.

## 그래서 언제 무엇을 쓰나요?

- **rebase**: 아직 나만 쓰는 로컬 브랜치를 최신 `main`에 맞출 때, PR을 올리기 전에 커밋을 정리할 때 (`git rebase -i`)
- **merge**: 여러 사람이 함께 쓰는 브랜치를 합칠 때, 브랜치의 흐름을 기록으로 남기고 싶을 때

팀마다 규칙이 다르므로(예: "PR은 squash merge", "main 동기화는 rebase"), 처음에는 **팀의 컨벤션을 먼저 확인**하는 것이 가장 좋습니다.

## 한 줄 요약

**merge는 "기록을 그대로 두고 합치기", rebase는 "기록을 깔끔하게 다시 쓰고 합치기"입니다.** 공유한 커밋은 다시 쓰지 않는다는 원칙만 지키면 둘 다 안전하게 쓸 수 있습니다.
