# git rebase와 git merge의 차이

`git merge`와 `git rebase`는 둘 다 한 브랜치의 변경을 다른 브랜치에 합치는 명령입니다. 결과 코드는 같을 수 있지만 커밋 기록이 남는 모양이 다릅니다.

예를 들어 `main`에서 `feature` 브랜치를 만들어 작업하는 동안 다른 사람이 `main`에 새 커밋을 올렸다고 해 봅시다. 이제 `feature`에 `main`의 새 변경을 반영해야 합니다.

`git merge main`을 실행하면 Git은 두 브랜치의 끝을 잇는 병합 커밋을 새로 만듭니다. 기존 커밋은 하나도 바뀌지 않습니다. 그래서 언제 브랜치가 갈라졌고 언제 합쳐졌는지가 기록에 그대로 남습니다. 대신 병합이 잦으면 기록이 여러 갈래로 얽혀 읽기 어려워집니다. 합칠 브랜치가 갈라진 뒤 대상 브랜치에 새 커밋이 없으면 Git은 병합 커밋 없이 브랜치 포인터만 앞으로 옮깁니다. 이것을 fast-forward라고 합니다.

`git rebase main`을 실행하면 Git은 `feature`의 커밋을 떼어 내 `main`의 최신 커밋 뒤에 하나씩 다시 적용합니다. 그러면 기록이 한 줄로 곧게 이어지고, 처음부터 최신 `main`에서 작업을 시작한 것처럼 보입니다. 이때 다시 적용된 커밋은 내용이 같아도 해시가 다른 새 커밋입니다. 즉 rebase는 기록을 다시 씁니다.

```
merge 후:   A---B---C---F (main)
                 \     /
                  D---E        F는 병합 커밋

rebase 후:  A---B---C---D'---E' (feature)
                               D', E'는 새로 만든 커밋
```

이 차이 때문에 꼭 지켜야 할 규칙이 하나 있습니다. **다른 사람과 이미 공유한 커밋은 rebase하지 않습니다.** 원격 저장소에 올린 브랜치를 rebase하면 강제 푸시(`git push --force`)를 해야 하고, 그 브랜치를 받아 둔 동료의 기록과 어긋납니다. rebase는 아직 혼자만 가진 로컬 커밋을 정리할 때 씁니다.

충돌을 처리하는 방식도 다릅니다. merge는 충돌을 한 번에 모아서 해결합니다. rebase는 커밋을 하나씩 다시 적용하므로 커밋마다 충돌이 날 수 있습니다. 해결한 뒤 `git rebase --continue`로 진행하고, 중간에 그만두려면 `git rebase --abort`로 원래 상태로 돌아갑니다.

어느 쪽을 쓸지는 팀의 규칙을 먼저 따릅니다. 팀에 정해진 규칙이 없다면 이렇게 나눠 쓰는 경우가 많습니다. 내 로컬 브랜치를 최신 `main`에 맞출 때는 rebase를 쓰고, 공유 브랜치끼리 합칠 때는 merge를 씁니다.
