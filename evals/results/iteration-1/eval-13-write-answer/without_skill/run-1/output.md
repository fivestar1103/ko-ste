# git merge와 git rebase, 뭐가 다를까?

브랜치에서 작업을 마치면 그 결과를 `main` 같은 다른 브랜치에 합쳐야 합니다. 이때 쓰는 방법이 `merge`와 `rebase`입니다. 결과 코드는 같아도 **히스토리(커밋 기록)가 남는 모양**이 다릅니다.

## 상황 예시

`main`에서 `feature` 브랜치를 만들어 작업하는 동안, 다른 사람이 `main`에 새 커밋을 올렸다고 해 봅시다.

```
      A---B  (feature)
     /
C---D---E    (main)
```

## git merge: 두 갈래를 그대로 합친다

```bash
git switch feature
git merge main
```

```
      A---B---M  (feature)
     /       /
C---D---E----
```

- 두 브랜치를 잇는 **머지 커밋(M)**이 새로 생깁니다.
- 기존 커밋은 하나도 바뀌지 않습니다. **실제로 일어난 일이 그대로 남습니다.**
- 대신 브랜치가 많아지면 히스토리 그래프가 복잡해집니다.

## git rebase: 내 커밋을 최신 위치로 옮겨 다시 쌓는다

```bash
git switch feature
git rebase main
```

```
C---D---E---A'---B'  (feature)
```

- 내 커밋 A, B를 `main`의 최신 커밋(E) 뒤에 **다시 적용합니다.**
- 히스토리가 **한 줄로 깔끔해집니다.**
- 대신 A, B는 해시가 다른 **새 커밋 A', B'**가 됩니다. 기존 커밋이 사라지고 다시 만들어지는 셈입니다.

## 한눈에 비교

| | merge | rebase |
|---|---|---|
| 히스토리 모양 | 갈래가 그대로 남음 | 한 줄로 정리됨 |
| 기존 커밋 | 바뀌지 않음 | 새 커밋으로 다시 작성됨 |
| 머지 커밋 | 생김 | 안 생김 |
| 충돌 해결 | 한 번에 | 커밋마다 따로 할 수 있음 |
| 안전성 | 높음 | 공유 브랜치에서는 주의해야 함 |

## 꼭 기억할 규칙

> **이미 push해서 다른 사람과 공유한 브랜치는 rebase하지 마세요.**

rebase는 커밋을 다시 쓰기 때문에, 다른 사람이 가진 기존 커밋과 내 새 커밋이 서로 어긋납니다. 이걸 억지로 올리려면 `git push --force`를 써야 하고, 그러면 동료의 작업이 꼬이거나 사라질 수 있습니다.

## 그래서 언제 뭘 쓰나요?

- **아직 혼자 쓰는 로컬 브랜치를 최신 `main`에 맞출 때** → `rebase`로 히스토리를 깔끔하게
- **공유 브랜치나 `main`에 작업을 합칠 때** → `merge`로 안전하게
- **팀 규칙이 있다면** → 팀 규칙을 따르세요. 팀마다 "squash merge만 쓴다", "PR 전에 꼭 rebase한다"처럼 정해 둔 방식이 있습니다.

정리하면 **merge는 "있었던 일을 그대로 기록"하고, rebase는 "처음부터 최신 코드 위에서 작업한 것처럼 다시 정리"합니다.** 둘 다 알아 두고 상황에 맞게 고르면 됩니다.
