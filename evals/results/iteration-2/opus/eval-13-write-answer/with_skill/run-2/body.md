# git merge와 git rebase의 차이

두 명령은 모두 한 브랜치의 변경을 다른 브랜치에 합친다. 둘의 차이는 합친 뒤에 이력이 어떤 모양으로 남는가에 있다.

예를 들어 main에서 feature 브랜치를 만들고 커밋 C와 D를 쌓았다고 하자. 그동안 다른 사람이 main에 커밋 E를 올렸다.

```
      C---D   feature
     /
A---B---E     main
```

## merge

feature 브랜치에서 `git merge main`을 실행하면 Git은 두 브랜치의 끝을 잇는 새 커밋 M을 만든다. 이 커밋을 병합 커밋이라고 한다.

```
      C---D---M   feature
     /       /
A---B-------E     main
```

C와 D는 그대로 남는다. 그래서 두 브랜치가 언제 갈라졌고 언제 합쳐졌는지가 이력에 드러난다. 다만 브랜치를 자주 합치면 병합 커밋이 쌓여서 이력을 따라가기 어려워진다.

## rebase

feature 브랜치에서 `git rebase main`을 실행하면 Git은 C와 D의 변경을 E 뒤에 하나씩 다시 적용한다. 그 결과 처음부터 E 위에서 작업한 것처럼 이력이 한 줄로 이어진다.

```
A---B---E---C'---D'   feature
```

C'와 D'는 C와 D의 변경을 다시 적용해서 만든 새 커밋이다. 그래서 해시가 C, D와 다르다. 이력은 깔끔해지지만 브랜치가 갈라졌던 지점은 이력에 남지 않는다.

## 주의할 점

rebase는 기존 커밋을 새 커밋으로 바꾼다. 그래서 이미 원격 저장소에 올려 다른 사람과 함께 쓰는 커밋은 rebase하지 않는 것이 좋다. 그런 커밋을 rebase하면 강제 푸시(`git push --force`)를 해야 한다. 이때 동료의 로컬 이력과 원격 이력이 어긋나서 같은 변경이 두 번 들어가거나 충돌이 생길 수 있다.

흔히 쓰는 기준은 이렇다. 혼자 쓰는 브랜치를 최신 main에 맞출 때는 rebase를 쓰고, 공유하는 브랜치를 합칠 때는 merge를 쓴다. 팀마다 정해 둔 규칙이 따로 있을 수 있으니 처음 합치기 전에 팀의 규칙을 확인한다.
