# git merge와 git rebase는 어떻게 다를까?

두 명령은 목적이 같습니다. 한 브랜치의 변경 사항을 다른 브랜치에 합칩니다. 차이는 **히스토리를 어떻게 남기느냐**에 있습니다.

## 상황

`main`에서 `feature` 브랜치를 따서 작업하는 동안 다른 사람이 `main`에 새 커밋을 올렸다고 해 봅시다.

```
        A---B  (feature)
       /
  C---D---E  (main)
```

## git merge: 두 갈래를 그대로 두고 합치기

```bash
git checkout feature
git merge main
```

```
        A---B---M  (feature)
       /       /
  C---D---E---
```

- 두 브랜치를 잇는 **머지 커밋(M)**이 새로 생깁니다.
- 기존 커밋은 하나도 바뀌지 않습니다. 실제로 일어난 일이 그대로 기록됩니다.
- 대신 브랜치가 많아지면 히스토리가 갈래로 얽혀 읽기 어려워집니다.

## git rebase: 내 커밋을 최신 지점 위로 옮기기

```bash
git checkout feature
git rebase main
```

```
  C---D---E---A'---B'  (feature)
```

- 내 커밋(A, B)을 `main`의 최신 커밋(E) 뒤에 **다시 적용**합니다.
- 히스토리가 한 줄로 깔끔해집니다.
- 단, A'와 B'는 내용이 같아도 **해시가 다른 새 커밋**입니다. 기존 커밋을 다시 쓰는 셈입니다.

## 한눈에 비교

| | merge | rebase |
|---|---|---|
| 히스토리 모양 | 갈래가 남음 | 한 줄로 정리됨 |
| 기존 커밋 | 그대로 유지 | 새 커밋으로 바뀜 |
| 머지 커밋 | 생김 | 생기지 않음 |
| 충돌 해결 | 한 번에 처리 | 커밋마다 처리할 수 있음 |
| 안전성 | 높음 | 공유된 브랜치에서는 위험 |

## 꼭 기억할 규칙

> **이미 push해서 다른 사람과 공유한 브랜치는 rebase하지 마세요.**

rebase는 커밋을 새로 만들기 때문에 같은 브랜치를 받아 간 동료의 히스토리와 어긋납니다. 이때 `git push --force`를 쓰면 동료의 작업이 꼬이거나 사라질 수 있습니다.

## 언제 무엇을 쓸까?

- **rebase**: 아직 나만 쓰는 로컬 브랜치를 최신 `main`에 맞출 때, PR을 올리기 전에 커밋을 정리할 때
- **merge**: 공유 브랜치를 합칠 때, 브랜치가 언제 합쳐졌는지 기록을 남기고 싶을 때

팀마다 정해 둔 방식(예: "PR은 squash merge", "로컬에서는 rebase")이 있다면 그 규칙을 먼저 따르세요. 잘 모르겠다면 **merge가 더 안전한 선택**입니다.
