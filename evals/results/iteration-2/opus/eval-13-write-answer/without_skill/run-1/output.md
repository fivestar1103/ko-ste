# git merge와 git rebase는 어떻게 다를까?

혼자 작업하던 브랜치를 `main`에 합치는 방법은 크게 두 가지입니다. 둘 다 "다른 브랜치의 변경 사항을 내 브랜치에 반영한다"는 목적은 같습니다. 차이는 **히스토리를 어떤 모양으로 남기느냐**에 있습니다.

## 상황 예시

`main`에서 `feature` 브랜치를 만들어 작업하는 동안, 다른 사람이 `main`에 새 커밋을 올렸다고 해 봅시다.

```
      A---B  (feature)
     /
C---D---E    (main)
```

## git merge: 두 갈래를 그대로 두고 합친다

```bash
git switch feature
git merge main
```

```
      A---B---M  (feature)
     /       /
C---D---E----
```

- 두 브랜치를 잇는 **병합 커밋(M)** 이 새로 생깁니다.
- 기존 커밋 A와 B는 **그대로 남습니다.**
- 히스토리에 "언제 갈라졌고 언제 합쳐졌는지"가 정확하게 기록됩니다.
- 대신 브랜치가 많아지면 그래프가 복잡해집니다.

## git rebase: 내 커밋을 최신 main 위로 옮긴다

```bash
git switch feature
git rebase main
```

```
C---D---E---A'---B'  (feature)
```

- 내 커밋 A와 B를 떼어 낸 다음, 최신 `main`(E) 위에 **다시 적용합니다.**
- 그래서 A', B'는 내용은 같아도 **해시가 다른 새 커밋**입니다.
- 히스토리가 한 줄로 깔끔하게 정리됩니다.
- 대신 "원래는 따로 작업했다"는 흔적이 사라집니다.

## 한눈에 비교

| 구분 | merge | rebase |
|---|---|---|
| 히스토리 모양 | 갈래가 그대로 남음 | 일직선 |
| 기존 커밋 | 유지 | 새 커밋으로 바뀜 |
| 병합 커밋 | 생김 | 생기지 않음 |
| 충돌 해결 | 한 번에 처리 | 커밋마다 따로 처리할 수 있음 |
| 위험도 | 낮음 | 공유된 브랜치에서 쓰면 위험 |

## 꼭 기억할 규칙

> **이미 다른 사람과 공유한(push한) 커밋은 rebase하지 마세요.**

rebase는 커밋을 새로 만들기 때문에, 동료가 가진 히스토리와 내 히스토리가 어긋납니다. 이 상태에서 `git push --force`를 하면 동료의 작업이 꼬이거나 사라질 수 있습니다.

## 그래서 언제 무엇을 쓰나요?

- **아직 나만 쓰는 로컬 브랜치를 최신 main에 맞출 때** → `rebase`
- **공유 브랜치에 기능을 합칠 때** → `merge`(또는 팀이 정한 PR 병합 방식)
- **잘 모르겠을 때** → `merge`가 안전합니다.

마지막으로, 팀마다 선호하는 방식이 다릅니다. 무엇을 쓸지 혼자 정하기보다 먼저 **팀의 컨벤션을 확인하세요.**
