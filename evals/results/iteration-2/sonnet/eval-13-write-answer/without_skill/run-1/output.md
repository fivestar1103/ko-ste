# git rebase vs git merge, 한눈에 이해하기

두 명령은 **"다른 브랜치의 작업을 내 브랜치에 합친다"**는 목적은 같습니다. 다만 히스토리를 남기는 방식이 다릅니다.

## 상황 가정

`main`에서 `feature` 브랜치를 만들어 작업하는 동안, 다른 사람이 `main`에 새 커밋을 올렸습니다.

```
      A---B---C   feature
     /
D---E---F---G     main
```

## git merge: 두 흐름을 "합치는 커밋"으로 묶는다

```bash
git checkout feature
git merge main
```

```
      A---B---C---M   feature
     /           /
D---E---F-------G     main
```

- 두 브랜치를 이어 주는 **머지 커밋(M)**이 새로 생깁니다.
- 기존 커밋은 전혀 바뀌지 않습니다. 실제로 일어난 작업 순서가 그대로 남습니다.
- 단점: 머지가 반복되면 히스토리가 갈래갈래 복잡해집니다.

## git rebase: 내 커밋을 최신 main 위로 "옮겨 붙인다"

```bash
git checkout feature
git rebase main
```

```
              A'--B'--C'   feature
             /
D---E---F---G              main
```

- `feature`의 커밋들을 `main`의 최신 지점(G) 뒤에 **다시 만들어 붙입니다.**
- 히스토리가 한 줄로 깔끔해집니다.
- 주의: A', B', C'는 원래 A, B, C와 **해시가 다른 새 커밋**입니다. 즉, 히스토리를 다시 쓰는 것입니다.

## 한 줄 비교

| | merge | rebase |
|---|---|---|
| 히스토리 | 분기와 합류가 그대로 보임 | 일직선으로 정리됨 |
| 기존 커밋 | 유지 | 새 커밋으로 교체 |
| 머지 커밋 | 생김 | 안 생김 |
| 안전성 | 높음 | 주의 필요 |

## 꼭 지킬 황금률

> **이미 push해서 다른 사람과 공유한 브랜치는 rebase하지 마세요.**

커밋 해시가 바뀌기 때문에, 같은 브랜치를 쓰는 동료의 히스토리와 어긋나 큰 혼란이 생깁니다.

## 실무 가이드

- **내 로컬 브랜치를 최신 main에 맞추고 싶을 때** → `rebase`
- **공유 브랜치나 `main`에 작업을 합칠 때** → `merge` (팀 규칙을 먼저 확인하세요)
- 헷갈리면 `merge`가 더 안전합니다. rebase 중 충돌이 나서 막히면 `git rebase --abort`로 언제든 원상복구할 수 있습니다.

둘 중 무엇이 "정답"인지는 없고, 팀의 규칙과 상황에 맞게 고르는 것이 중요합니다.
